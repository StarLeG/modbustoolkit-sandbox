# ADR-003: движок поведений — семантика и интеграция с картой

- **Статус:** принято
- **Дата:** 2026-10-29
- **Задача:** TASK-201…242 (Эпик 2)

## Контекст

Эпик 2 реализует движок поведений: привязка `(slave, area, address) → Behavior`,
тик 100 мс, `locked`-записи, дефолты. ТЗ и CLAUDE.md не описывают несколько
семантических развилок, которые приходится решить до кода.

## Решения

1. **`constant` не перетирает пользовательские записи.** Движок сравнивает
   очередное значение поведения с *последним записанным самим движком*
   (`last_written`) и пишет в карту только при изменении. Для `constant` это
   означает «применить один раз при установке/сбросе», далее запись FC 5/6/16
   от другого пользователя сохраняется (shared last-write-wins, инвариант 1).
   Временны́е поведения (counter, sawtooth, …) меняют значение и тем самым
   перезаписывают чужие записи — это документированное поведение
   («может быть перезаписано»). Альтернатива «constant пишет каждый тик»
   делает невозможным базовый сценарий наладчика (записал — прочитал).

2. **`counter` и `countdown` получают параметр `interval_s` (по умолчанию 1.0).**
   Инвариант 2 требует «IR — счётчик 1 Гц», а дефолт TASK-205 — `counter step=1`
   при тике 100 мс. Без интервала это 10 Гц. Шаг применяется раз в `interval_s`
   (не раз в тик); `interval_s=0.1` даёт счётчик на каждый тик.

3. **`locked` проверяется на входе записи, движок пишет мимо проверки.**
   Политика записи (`write_policy`) — колбэк в `SlaveMapContext.async_setValues`
   (и позже в REST-запись): окно, задевающее locked-привязку, целиком
   отклоняется с `0x04 Server Device Failure` + запись в журнал. Сам движок
   пишет в `SlaveMap` напрямую — иначе locked заблокировал бы собственный
   генератор. Привязка ведётся к value-grid адресам (1,3,…,1023), окно FC 6/16
   переводится в value-grid до проверки (для 32-битных форматов запись в
   регистр N+1 задевает значение по адресу N).

4. **Ошибка поведения → `constant 0` (инвариант 7).** Исключение из
   `update()` ловится движком, поведение в реестре заменяется на
   `Behavior("constant", {"value": 0})` с сохранением `locked`, пишется 0,
   пишется лог/журнал. Сервер и остальные поведения продолжают работать.

5. **Дефолты материализуются в реестре.** `BehaviorRegistry` при создании
   заполняет все допустимые привязки слейвов 1..9: CL/HR — `constant 0`
   (locked=False), IR — `counter step=1, interval_s=1` (locked=True),
   DI — `counter_bits` (бит адреса−1 счётчика секунд, locked=True).
   **Slave 10 исключён** из поведений: его IR вычисляется (`slave10.read_registers`).
   Один экземпляр `Behavior`-дефолта разделяется многими привязками;
   `set()` подменяет объект, движок замечает смену по идентичности.
   Состав дефолтов уточнён в ADR-009 (витрина IR/HR, случайные биты DI 1..8).

6. **Привязка — value-grid адрес** (`SlaveSpec.area_ranges`): для слейвов 2..9
   нечётные 1,3,…,1023. Запись движка кодируется через `codec.encode` в
   `registers_per_value` регистров начиная с этого адреса.

7. **Время поведений** — секунды от создания генератора (`update(now)`),
   детерминированно тестируется фиктивным временем. Параметр `phase` — доля
   периода (0..1), задаёт начальное смещение. Случайные поведения принимают
   `random.Random` для детерминированных тестов.

## Последствия

- `constant 0` на HR/CL не мешает записи из UI/Modbus — базовый сценарий работает.
- Дефолтный реестр ~6 тыс. привязок; движок тикает только по неизменившимся
  генераторам и пишет лишь изменения — стоимость тика пропорциональна числу
  *активных* (нестатичных) поведений.
- `interval_s` — расширение параметров counter/countdown относительно текста
  ISSUES.md (там параметры перечислены без интервала); зафиксировано здесь.
