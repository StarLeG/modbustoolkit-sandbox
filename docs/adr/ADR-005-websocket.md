# ADR-005: WebSocket live-состояние и канал событий

- **Статус:** принято
- **Дата:** 2026-10-29
- **Задача:** TASK-401…404 (Эпик 4)

## Контекст

Эпик 4 добавляет live-состояние регистров (`/ws/state`) и канал событий
(`/ws/events`) поверх тех же in-process сервисов (ADR-004). CLAUDE.md задаёт
путь `/ws/state` и `WS_STATE_HZ`, но не описывает: протокол подписки, политику
backpressure для медленных клиентов (TASK-403), источник событий для канала
событий и жизненный цикл рассылки. Эти развилки решаются до кода.

## Решения

1. **Модули web-слоя:** `app/api/state_view.py` — построение value-grid
   представления значений (общее с `GET /api/modbus/state` и снимками);
   `app/api/state_bus.py` — `WebStateBus` (клиенты, очереди, рассылка) без
   FastAPI-зависимостей; `app/api/ws.py` — WS-эндпоинты (`ws_router`, пути
   `/ws/state` и `/ws/events` — вне префикса `/api/modbus`, как `GET /healthz`).
   `WebStateBus` входит в `AppServices` (ADR-004 п. 1).

2. **Протокол `/ws/state` (TASK-401).** Первый текстовый кадр клиента —
   JSON-подписка `{"slave": 1, "areas": ["hr", "cl"], "addresses": [1, 3]}`:
   `slave` обязателен (1..10), `areas` — по умолчанию все области слейва,
   `addresses` — по умолчанию вся сетка значений (value-grid: 1,3,…,1023 для
   32-битных форматов). Повторное сообщение — переподписка. Ответ — кадры
   `{"type": "state", "slave", "fmt", "areas"}` (формат `GET /api/modbus/state`).
   Ошибка подписки → `{"type": "error", "detail": …}` + close(1008). Первый
   кадр состояния отправляется сразу после подписки — подтверждение.

3. **Периодическая рассылка (TASK-402).** Один тикер `WebStateBus` с периодом
   `1 / WS_STATE_HZ` (по умолчанию 2 Гц) ставит кадры в очереди клиентов.
   Тикер поднимается лениво при первом state-клиенте и останавливается с уходом
   последнего — lifespan не меняется, тесты с `run_engine=False` детерминированы.

4. **Backpressure (TASK-403).** У каждого клиента ограниченная очередь
   (константа `WS_CLIENT_QUEUE`, не env — деплою не нужна); продюсеры (тикер,
   журнал) кладут через `put_nowait` и никогда не ждут клиента. Переполнение
   очереди = клиент не успевает → он отключается (close 1013), остальные
   продолжают получать кадры. Отправка защищена таймаутом `WS_SEND_TIMEOUT_S`;
   превышение — тоже отключение. Жалобы на «медленность» в журнал не пишутся
   (шум), фиксируется только закрытие.

5. **Канал событий `/ws/events` (TASK-404) — зеркало журнала.** События — это
   записи `JournalEntry` (поведения, записи, инъекции, отказы locked — ADR-004
   п. 7). Ядро расширяется минимально: `Journal.subscribe(listener)` —
   подписка на `add`, с отпиской; ошибка слушателя не прерывает `add`
   (инвариант 7 — только лог). Кадр: `{"type": "event", "action", "slave",
   "area", "address", "value", "source", "ip", "timestamp"}`. Входящие кадры
   от клиента игнорируются. Тонкость: sync REST-хендлеры работают в threadpool,
   поэтому `publish_entry` передаёт кадр в event loop через
   `call_soon_threadsafe` — очереди клиентов трогаются только из loop
   (инвариант 6).

## Последствия

- UI (Эпик 7) подписывается на `/ws/state` без REST-поллинга; формат кадра
  совпадает с `GET /api/modbus/state`, переключение UI → 1:1.
- Клиенты без подписки кадров не получают; ресурс соединения — только очередь.
- Медленный клиент не влияет на остальных (свои задачи отправки) — требование
  TASK-403 проверяется юнит-тестами на фиктивных WS + интеграционным TestClient.
