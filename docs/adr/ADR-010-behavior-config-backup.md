# ADR-010: бэкап конфига поведений без персистентности

- **Статус:** принято
- **Дата:** 2026-10-31
- **Задача:** TASK-906

## Контекст

Инвариант 9 (CLAUDE.md): значения регистров живут в памяти, перезапуск их
сбрасывает; конфиг поведений сохранять можно, но только если в проекте уже
есть Redis/БД. Нет ни того, ни другого, и добавлять хранилище ради десятка
настроек непропорционально: правила проекта требуют минимума зависимостей,
а публичный сервер рассчитан на сброс состояния при каждом старте.

TASK-906 предлагает бэкап конфига поведений «если включаем персистентность».
Решение о персистентности - архитектурное, отсюда ADR.

## Решения

1. **Персистентность не вводим.** Никаких Redis/БД/файловых хранилищ под
   значения регистров и авто-сейвов конфига: перезапуск остаётся честным
   сбросом к демо-поведениям (ADR-009), поведение сервера предсказуемо.

2. **Бэкап конфига поведений - ручной экспорт и импорт JSON через REST.**
   Уже существующая пара эндпоинтов делает всю работу:
   `GET /api/modbus/behaviors` отдаёт полный конфиг, `POST /api/modbus/behaviors/batch`
   применяет пакет атомарно. В файл попадают только переопределения
   (привязки с `is_default=false`): демо-дефолты воспроизводятся кодом
   и при восстановлении не перетираются.

3. **`scripts/backup_config.py` - CLI-обёртка для администратора.**
   `save` выгружает переопределения в файл, `load` заливает их обратно через
   batch. Без сторонних зависимостей (urllib), как и остальные скрипты.

Значения регистров в бэкап не входят и не должны: это live-состояние
многопользовательского сервера (инвариант 1), а не конфигурация.
