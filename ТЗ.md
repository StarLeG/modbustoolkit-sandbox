# CLAUDE.md — контекст проекта для Claude Code

## О проекте

**modbustoolkit.electroman.by** — публичный набор инструментов для инженеров АСУ ТП
и наладчиков. В рамках этой итерации добавляем раздел
**«Публичный тестовый Modbus-TCP сервер»** — бесплатную многопользовательскую среду
для проверки Modbus-TCP клиентов.

### Что делает сервер
- Слушает TCP, эмулирует **10 unit ID** (slave 1..10).
- Поддерживает Modbus-функции: **1, 2, 3, 4, 5, 6, 16** (0x0F и прочее — запрещены).
- Значения регистров/coils живут в памяти и генерируются **движком поведений**
  (counter, sawtooth, triangle, meander, sine, random, constant и т.д.).
- Клиенты (наладчики) одновременно подключаются и работают — сервер многопользовательский.
- Web UI показывает live-состояние, позволяет настраивать поведения, инжектить ошибки,
  снимать/восстанавливать снимки.

### Источник истины по форматам
`docs/HRIR_SPEC.md` — спецификация форматов HR/IR по слейвам (uint16 / uint32 ABCD/CDAB/BADC/DCBA /
float ABCD/CDAB/BADC/DCBA, slave 10 — часовые пояса + Unix timestamp).

## Стек и архитектура (ожидаемые)

> **Первое, что нужно сделать при старте:** прочитать проект и подтвердить стек.
> Ниже — целевой стек; если в проекте уже есть FastAPI/Redis/Docker — использовать их.

- **Python 3.11+**, `asyncio`.
- **pymodbus** (async) — Modbus-TCP сервер, `ModbusServerContext(single=False)`.
- **FastAPI + uvicorn** — REST + WebSocket.
- **Docker / docker-compose** — деплой.
- **nginx** — reverse-proxy для HTTP/WS (Modbus-порт — отдельный TCP).
- Тесты: **pytest + pytest-asyncio**.
- Линтеры: **ruff**, типы: **mypy** (strict там, где принято в проекте).

### Схема процессов
```

┌──────────────────────────────────────────────────────────┐
│  uvicorn (FastAPI)                                       │
│   ├─ REST /api/modbus/*                                  │
│   ├─ WS   /ws/state                                      │
│   └─ сервисы: Engine (tick 100ms), WebStateBus, Journal  │
├──────────────────────────────────────────────────────────┤
│  pymodbus async server (TCP :5020)                       │
│   └─ 10 unit ID, доступ к тому же Engine (in-proc)       │
└──────────────────────────────────────────────────────────┘

```

Modbus-сервер и FastAPI живут в **одном event loop**, состояние — in-memory.

## Ключевые инварианты (не нарушать)

1. **HR/CL — shared last-write-wins.** Значения общие, могут быть перезаписаны другим пользователем.
   Это документируется в UI явно, не «исправляется».
2. **IR/DI — генерируются автоматически** (по умолчанию: IR — счётчик 1 Гц, DI — авто-паттерн).
3. **Slave 10 — только IR.** CL/DI/HR на нём отсутствуют → exception 0x02.
4. **Функция 16 — только для HR, максимум 2 регистра за запись.**
5. **Функции, кроме 1,2,3,4,5,6,16 — Illegal Function (0x01).**
6. **Event loop не блокируется.** Никаких `time.sleep`, синхронного I/O в горячем пути.
7. **Ошибка в поведении не роняет сервер.** try/except + лог + поведение переходит в `constant 0`.
8. **Секреты — только через env**, никогда в коде.
9. **Persistent storage для значений регистров отсутствует.** Перезапуск = сброс. Конфиг поведений
   можно сохранять (если в проекте уже есть Redis/БД), но это опция.

## Карта регистров (сводка)

Полная версия — в `docs/HRIR_SPEC.md`. Кратко:

| Slave | HR/IR формат | Адреса HR | Адреса IR | CL | DI |
|---|---|---|---|---|---|
| 1 | uint16 AB | 1..1024 | 1..1024 | 1..64 | 1..64 |
| 2 | uint32 ABCD | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 3 | uint32 CDAB | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 4 | uint32 BADC | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 5 | uint32 DCBA | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 6 | float ABCD | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 7 | float CDAB | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 8 | float BADC | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 9 | float DCBA | 1,3,…,1023 | 1,3,…,1023 | 1..64 | 1..64 |
| 10 | uint16 AB (IR only) | — | 1..268, 300..301 | — | — |

Slave 10: `1 + 10*Z` … `8 + 10*Z`, Z=0..26 (0..14 → UTC+00..UTC+14; 15..26 → UTC−01..UTC−12).
IR 300..301 — Unix timestamp, uint32 ABCD, точность ±0.5 с. «Дырки» в блоках → 0.

## Движок поведений (сводка API)

```python
class Behavior:
    kind: Literal["constant","counter","sawtooth","triangle","meander","sine",
                  "random_uniform","random_walk","ramp_oneshot","countdown",
                  "step","follow","toggle","pwm","random_bit","counter_bits","follow_bit"]
    params: dict
    locked: bool = False
```

- Тик 100 мс; привязка `(slave, area, address) → Behavior`.
- `locked=True` → Modbus-запись игнорируется (возвращать 0x04 Server Failure + запись в журнал).
- REST:
  - `GET    /api/modbus/behaviors`
  - `PUT    /api/modbus/behaviors/{slave}/{area}/{address}`
  - `POST   /api/modbus/behaviors/batch`
  - `POST   /api/modbus/behaviors/reset` (`all` или `{slave}`)

## Соглашения по коду

- Все публичные модули — с type hints; mypy там, где в проекте включён.
- Логирование — `structlog` или `logging` в формате проекта; никаких `print`.
- Тесты рядом с кодом: `tests/` (unit) и `tests/integration/` (pymodbus-клиент).
- Никаких «магических» портов/адресов — только через константы и env.
- REST-роуты — префикс `/api/modbus/`; WS — `/ws/state`.
- Имена слейвов/областей — строго `slave:int`, `area: Literal["cl","di","hr","ir"]`.

8. Все новые env-переменные — в `.env.example` и в `CLAUDE.md` (секция «Env»).
9. Перед PR — `pytest`, `ruff check`, `mypy` должны быть зелёными.

    добавить запись в `docs/adr/` (Architecture Decision Record).

# Спецификация форматов HR/IR

> Источник: внутренняя спецификация тестового сервера. Нормализовано для репозитория.

## Общее

Тестовый сервер предоставляет данные для **Holding Registers (HR)** и
**Input Registers (IR)** в нескольких форматах, отличающихся типом данных и
порядком байтов/слов. Обозначения: **A — старший байт**, **D — младший байт**
(для 32-битного значения ABCD: A=MSB, D=LSB).

Каждый slave отдаёт данные в своём формате. Регистры нумеруются **с 1**
(1-based, как в спецификации Modbus).

---

## Таблица форматов

| Slave | Формат | Описание | Адреса HR | Адреса IR | Байт на значение |
|---|---|---|---|---|---|
| 1 | `UINT16` | Беззнаковое 16-бит, порядок A B | 1,2,3,…,1024 | 1,2,3,…,1024 | 2 |
| 2 | `UINT32_ABCD` | Беззнаковое 32-бит, A B C D | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 3 | `UINT32_CDAB` | Беззнаковое 32-бит, C D A B | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 4 | `UINT32_BADC` | Беззнаковое 32-бит, B A D C | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 5 | `UINT32_DCBA` | Беззнаковое 32-бит, D C B A | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 6 | `FLOAT_ABCD` | IEEE-754 single, A B C D | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 7 | `FLOAT_CDAB` | IEEE-754 single, C D A B | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 8 | `FLOAT_BADC` | IEEE-754 single, B A D C | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 9 | `FLOAT_DCBA` | IEEE-754 single, D C B A | 1,3,5,…,1023 | 1,3,5,…,1023 | 4 |
| 10 | `UINT16` | Беззнаковое 16-бит, порядок A B | — | 1,2,3,…,268 и 300,301 | 2 (для 268), 4 (для 300,301) |

**32-битные значения** занимают **2 регистра**: значение по адресу `N` читается
из регистров `N` и `N+1`. Адрес следующего значения — `N+2`.

---

## Slave 10 — метрики времени по часовым поясам

На slave 10 **только IR** (CL/DI/HR отсутствуют, попытки чтения → exception 0x02).

### Блоки по часовым поясам

Для каждой зоны `Z` (0..26) — 8 метрик со смещением 10:

| Смещение | Метрика | Тип |
|---|---|---|
| `1 + 10*Z` | Год | UINT16 |
| `2 + 10*Z` | Месяц (1..12) | UINT16 |
| `3 + 10*Z` | День месяца (1..31) | UINT16 |
| `4 + 10*Z` | Час (0..23) | UINT16 |
| `5 + 10*Z` | Минута (0..59) | UINT16 |
| `6 + 10*Z` | Секунда (0..59) | UINT16 |
| `7 + 10*Z` | День недели (1=Пн..7=Вс) | UINT16 |
| `8 + 10*Z` | Смещение в часах от UTC (со знаком, int16) | INT16 |
| `9 + 10*Z` | *резерв* → 0 | UINT16 |
| `10 + 10*Z` | *резерв* → 0 | UINT16 |

`Z` — индекс зоны:

- `Z = 0..14` → UTC+00:00 … UTC+14:00 (к востоку от Гринвича)
- `Z = 15..26` → UTC−01:00 … UTC−12:00 (к западу, в обратном порядке)

Последняя зона `Z = 26` → адреса 261..270; но блок `1..268` покрывает все
используемые метрики (верхние «дырки» 269, 270 — за пределами карты).

### Примеры расчёта адресов

**Гринвич (UTC+00:00), Z = 0:**

- Год:  `1 + 10*0 = 1`
- Час:  `4 + 10*0 = 4`

**Москва (UTC+03:00), Z = 3:**

- Год:  `1 + 10*3 = 31`
- Час:  `4 + 10*3 = 34`

**UTC−05:00, Z = 19** (15 → −1, 19 → −5):

- Час:  `4 + 10*19 = 194`

### Unix Timestamp

| Адрес IR | Формат | Описание |
|---|---|---|
| 300, 301 | `UINT32_ABCD` | Unix timestamp (секунды с 1970-01-01 UTC), точность ±0.5 с |

---

## Примеры раскодирования (для тестов)

Вход: 4 байта `0x12 0x34 0x56 0x78` (один регистр = 2 байта):

| Порядок | Байты (A B C D) | uint32 | float (hex) |
|---|---|---|---|
| ABCD | `12 34 56 78` | `0x12345678 = 305419896` | `0x12345678 ≈ 5.6904566139e-28` |
| CDAB | `56 78 12 34` | `0x56781234 = 1450766900` | `0x56781234 ≈ 1.03e13` |
| BADC | `34 12 78 56` | `0x34127856 = 873364566` | `0x34127856 ≈ 1.37e-57` |
| DCBA | `78 56 34 12` | `0x78563412 = 2018915346` | `0x78563412 ≈ 2.44e34` |

> Примечание: значения float — для справки, точные цифры зависят от платформы;
> в тестах используются `struct.pack/unpack` round-trip.

---

## Соглашения реализации

- Внутреннее представление — **unpacked Python-значения** (`int` для uint16/uint32, `float`
  для FLOAT); кодек конвертирует в регистры при чтении/записи.
- Для `INT16` (смещение UTC) — `struct.pack(">h", value)`.
- Порядок байтов внутри регистра — **big-endian** (Modbus-стандарт, A — старший байт).
- Порядок слов — задаётся форматом (ABCD/CDAB/BADC/DCBA).
- Запись в HR slave N принимает **ровно** значение в формате этого slave.
```

## 📄 `docs/adr/ADR-001-architecture.md`

```markdown
# ADR-001 · Архитектура Modbus Test Server

- **Статус:** Accepted
- **Дата:** 2026-10-29
- **Контекст:** задача TASK-001/002 — добавление публичного тестового Modbus-TCP
  сервера на modbustoolkit.electroman.by

## Контекст

На сайт добавляется раздел «Публичный тестовый Modbus-TCP сервер» — бесплатная
многопользовательская среда для проверки Modbus-TCP клиентов инженерами-наладчиками.

Требования, влияющие на архитектуру:

1. **10 unit ID** с разными форматами HR/IR (uint16/uint32/float × ABCD/CDAB/BADC/DCBA),
   slave 10 — только IR с метриками часовых поясов.
2. **Многопользовательский режим** — десятки одновременных Modbus-клиентов и
   несколько web-сессий; общее состояние (HR/CL — «общая доска»).
3. **Движок поведений** — генерация значений (counter, sawtooth, triangle, …) с тиком ~10 Гц.
4. **Публичный доступ** без аутентификации Modbus (по природе протокола).
5. **Публичный web UI** без авторизации с live-обновлениями.
6. **Инъекция ошибок** (exception, delay, timeout) — для проверки обработки ошибок клиентами.
7. **Нет постоянного хранения** значений регистров (перезапуск = сброс).

## Решение

### 1. Один процесс, один event loop

Modbus-сервер (`pymodbus`, async) и FastAPI (`uvicorn`) живут в **одном процессе
и одном asyncio event loop**.

**Альтернативы:**

- (a) Два процесса + Redis pub/sub для состояния.
- (b) Один процесс, два потока (sync pymodbus + FastAPI).
- (c) Один процесс, один loop (выбрано).

**Обоснование:**

- Состояние — in-memory, доступ к нему из обоих сервисов бесплатный и атомарный
  в пределах одного loop; нет сети между сервисами, нет сериализации.
- Движок поведений — та же asyncio-задача, тикает 10 Гц; синхронизация не нужна.
- `pymodbus` поддерживает async API — второй поток не требуется.
- Проще деплой (один контейнер), проще отладка, меньше движущихся частей.

**Цена:** масштабирование по CPU ограничено одним loop. Для целевой нагрузки
(50–200 клиентов, 10 Гц движок) — с запасом. При росте — переход к варианту (a)
без изменения внешнего API.

### 2. In-memory state, без персистентности

- Значения регистров, поведений, журнал событий, инъекции — в памяти.
- Конфиг поведений и снимки — **опционально** в Redis/файл, если в проекте уже есть.
- Перезапуск сервиса сбрасывает всё — это документировано в UI.

**Обоснование:** тестовый сервер, «эфемерность» ожидаема. Персистентность
состояния усложняет код (гонки, миграции, восстановление) без пользы для сценария.

### 3. Modbus-TCP на порту **5020** по умолчанию

- Порт 502 — привилегированный (`<1024`), требует `root`/CAP_NET_BIND_SERVICE
  и часто блокируется публичными хостингами.
- Порт 5020 — безопасный дефолт; включается через `MODBUS_TCP_PORT`.
- Возможность поднять 502 — на усмотрение окружения (systemd `AmbientCapabilities`,
  docker `cap_add`).

### 4. Многопользовательская семантика: shared last-write-wins

- HR/CL доступны для записи всем; значения могут быть перезаписаны.
- IR/DI — read-only, генерируются движком.
- Настройки поведений — общие для всех; кто угодно может изменить.
- Плашка-предупреждение в UI — **обязательна**.

**Альтернативы:** изоляция сессий (каждому клиенту — свой виртуальный slave),
per-user overrides.

**Обоснование:** реальный Modbus не изолирует «клиентов» — они работают с одним
устройством. Изоляция сломала бы сценарий «два клиента конкурируют за регистр» —
а это как раз то, что полезно проверить наладчику. Rate-limit + журнал — вместо изоляции.

### 5. Защита публичного порта: лимиты, а не аутентификация

- `MODBUS_MAX_CONN_PER_IP` (20) — от залипания.
- `MODBUS_MAX_WRITE_PER_SEC` (200) и `WEB_MAX_WRITE_PER_MIN_PER_IP` (50) — от спама.
- Ring buffer журнала (1000) — для разбора инцидентов.
- Healthcheck, метрики.

**Обоснование:** Modbus не имеет аутентификации; любая «защита» — это либо
нестандартный протокол (ломает клиентов), либо сетевые лимиты. Последнее — безопасно
и не мешает легитимным клиентам.

### 6. Формат-зависимый кодек

Каждый slave знает свой формат (`uint16`, `uint32_abcd`, …, `float_dcba`). Кодек
`encode(value) -> list[int]` / `decode(regs) -> value` — единая точка конверсии.

**Обоснование:** централизация исключает рассинхрон; тесты по таблице раскодирования
(`HRIR_SPEC.md`) покрывают все 9 форматов.

## Последствия

**Положительные:**

- Минимум инфраструктуры: один контейнер, один процесс.
- Простое тестирование (in-process integration).
- Ясная модель «общая доска», совпадающая с реальным Modbus.
- Лёгкое добавление новых поведений (один класс + регистрация).

**Отрицательные / риски:**

- Один loop = один CPU по умолчанию. При росте нагрузки — горизонтальное
  масштабирование потребует Redis pub/sub (вариант a) — но это уже отдельный ADR.
- In-memory = потеря состояния при рестарте. Приемлемо для тестового сервера,
  но должно быть явно написано в UI.
- Публичный порт без аутентификации — возможен абьюз. Митигация — лимиты и журнал,
  при необходимости — временная блокировка IP на уровне nginx/fail2ban.

### Как импортировать

**Вариант A — bash (быстрее):**

```bash
cd scripts/github_issues
chmod +x create_issues.sh
gh auth status   # должен быть залогинен
./create_issues.sh <owner>/<repo>
```

**Вариант B — CSV через API (если не хочешь создавать label-ы вручную):**

```bash
# пример с gh + jq, создаёт задачи по одной
tail -n +2 issues.csv | while IFS=, read -r title body labels; do
  title=$(echo "$title" | sed 's/^"//;s/"$//')
  body=$(echo "$body" | sed 's/^"//;s/"$//')
  labels=$(echo "$labels" | sed 's/^"//;s/"$//')
  gh issue create --title "$title" --body "$body" --label "$labels"
done
```

**Вариант C — GitHub Projects:** после импорта в Issues — «Add to project», колонки
`Todo / In Progress / Review / Done`, swimlanes по label `P0/P1/P2`.

### Итог

| Артефакт | Назначение |
|---|---|
| `docs/HRIR_SPEC.md` | Единый источник истины по форматам HR/IR, с примерами расчёта адресов и раскодирования |
| `docs/adr/ADR-001-architecture.md` | Зафиксированные решения: один loop, in-memory, порт 5020, shared last-write-wins, лимиты вместо auth, формат-зависимый кодек — с обоснованиями и рисками |
| `scripts/github_issues/create_issues.sh` | Однокомандный импорт всех ~90 задач + labels в GitHub Issues |
| `scripts/github_issues/issues.csv` | Альтернативный путь импорта для тех, кто не любит `gh` |

Все три дополняют `CLAUDE.md` и `ISSUES.md` и замыкают контур: **спецификация → архитектурные решения → задачи → контекст для Claude Code**.
