# ADR-001 · Архитектура Modbus Test Server

- **Статус:** Accepted
- **Дата:** 2026-10-29
- **Контекст:** задача TASK-001/002 — добавление публичного тестового Modbus-TCP
  сервера на modbustoolkit.electroman.by

## Контекст

На сайт добавляется раздел «Публичный тестовый Modbus-TCP сервер» — бесплатная
многопользовательская среда для проверки Modbus-TCP клиентов инженерами-наладчиками.

Требования, влияющие на архитектуру:

1. **10 unit ID** с разными форматами HR/IR (uint16/uint32/float × ABCD/CDAB/BADC/DCBA),
   slave 10 — только IR с метриками часовых поясов.
2. **Многопользовательский режим** — десятки одновременных Modbus-клиентов и
   несколько web-сессий; общее состояние (HR/CL — «общая доска»).
3. **Движок поведений** — генерация значений (counter, sawtooth, triangle, …) с тиком ~10 Гц.
4. **Публичный доступ** без аутентификации Modbus (по природе протокола).
5. **Публичный web UI** без авторизации с live-обновлениями.
6. **Инъекция ошибок** (exception, delay, timeout) — для проверки обработки ошибок клиентами.
7. **Нет постоянного хранения** значений регистров (перезапуск = сброс).

## Решение

### 1. Один процесс, один event loop

Modbus-сервер (`pymodbus`, async) и FastAPI (`uvicorn`) живут в **одном процессе
и одном asyncio event loop**.

**Альтернативы:**

- (a) Два процесса + Redis pub/sub для состояния.
- (b) Один процесс, два потока (sync pymodbus + FastAPI).
- (c) Один процесс, один loop (выбрано).

**Обоснование:**

- Состояние — in-memory, доступ к нему из обоих сервисов бесплатный и атомарный
  в пределах одного loop; нет сети между сервисами, нет сериализации.
- Движок поведений — та же asyncio-задача, тикает 10 Гц; синхронизация не нужна.
- `pymodbus` поддерживает async API — второй поток не требуется.
- Проще деплой (один контейнер), проще отладка, меньше движущихся частей.

**Цена:** масштабирование по CPU ограничено одним loop. Для целевой нагрузки
(50–200 клиентов, 10 Гц движок) — с запасом. При росте — переход к варианту (a)
без изменения внешнего API.

### 2. In-memory state, без персистентности

- Значения регистров, поведений, журнал событий, инъекции — в памяти.
- Конфиг поведений и снимки — **опционально** в Redis/файл, если в проекте уже есть.
- Перезапуск сервиса сбрасывает всё — это документировано в UI.

**Обоснование:** тестовый сервер, «эфемерность» ожидаема. Персистентность
состояния усложняет код (гонки, миграции, восстановление) без пользы для сценария.

### 3. Modbus-TCP на порту **5020** по умолчанию

- Порт 502 — привилегированный (`<1024`), требует `root`/CAP_NET_BIND_SERVICE
  и часто блокируется публичными хостингами.
- Порт 5020 — безопасный дефолт; включается через `MODBUS_TCP_PORT`.
- Возможность поднять 502 — на усмотрение окружения (systemd `AmbientCapabilities`,
  docker `cap_add`).

### 4. Многопользовательская семантика: shared last-write-wins

- HR/CL доступны для записи всем; значения могут быть перезаписаны.
- IR/DI — read-only, генерируются движком.
- Настройки поведений — общие для всех; кто угодно может изменить.
- Плашка-предупреждение в UI — **обязательна**.

**Альтернативы:** изоляция сессий (каждому клиенту — свой виртуальный slave),
per-user overrides.

**Обоснование:** реальный Modbus не изолирует «клиентов» — они работают с одним
устройством. Изоляция сломала бы сценарий «два клиента конкурируют за регистр» —
а это как раз то, что полезно проверить наладчику. Rate-limit + журнал — вместо изоляции.

### 5. Защита публичного порта: лимиты, а не аутентификация

- `MODBUS_MAX_CONN_PER_IP` (20) — от залипания.
- `MODBUS_MAX_WRITE_PER_SEC` (200) и `WEB_MAX_WRITE_PER_MIN_PER_IP` (50) — от спама.
- Ring buffer журнала (1000) — для разбора инцидентов.
- Healthcheck, метрики.

**Обоснование:** Modbus не имеет аутентификации; любая «защита» — это либо
нестандартный протокол (ломает клиентов), либо сетевые лимиты. Последнее — безопасно
и не мешает легитимным клиентам.

### 6. Формат-зависимый кодек

Каждый slave знает свой формат (`uint16`, `uint32_abcd`, …, `float_dcba`). Кодек
`encode(value) -> list[int]` / `decode(regs) -> value` — единая точка конверсии.

**Обоснование:** централизация исключает рассинхрон; тесты по таблице раскодирования
(`HRIR_SPEC.md`) покрывают все 9 форматов.

## Последствия

**Положительные:**

- Минимум инфраструктуры: один контейнер, один процесс.
- Простое тестирование (in-process integration).
- Ясная модель «общая доска», совпадающая с реальным Modbus.
- Лёгкое добавление новых поведений (один класс + регистрация).

**Отрицательные / риски:**

- Один loop = один CPU по умолчанию. При росте нагрузки — горизонтальное
  масштабирование потребует Redis pub/sub (вариант a) — но это уже отдельный ADR.
- In-memory = потеря состояния при рестарте. Приемлемо для тестового сервера,
  но должно быть явно написано в UI.
- Публичный порт без аутентификации — возможен абьюз. Митигация — лимиты и журнал,
  при необходимости — временная блокировка IP на уровне nginx/fail2ban.
