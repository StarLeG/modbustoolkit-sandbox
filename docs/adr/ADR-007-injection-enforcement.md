# ADR-007: Enforcement инъекций ошибок

- **Статус:** принято
- **Дата:** 2026-10-29
- **Задача:** TASK-601…606 (Эпик 6); база — ADR-004 п. 6 (реестр), ADR-006 (точки enforcement)

## Контекст

Реестр инъекций (`app/modbus/injection.py`, TASK-309) уже хранит инъекции
`exception` / `delay` / `timeout` с ленивым TTL и снимает их через REST, но не
влияет на Modbus-запросы. Нужно решить: где в пути запроса применять инъекции,
как сопоставлять запрос с целью инъекции (слейв / диапазон), что отвечать для
каждого типа и как себя ведут пересекающиеся и истёкшие инъекции.

Ограничения: инвариант 6 (event loop не блокируется — задержки только
`asyncio.sleep`), инвариант 9 (in-memory), защита ring buffer журнала от флуда
(ADR-006 п. 3).

## Решения

1. **Точка enforcement** — `GuardedRequestHandler.handle_request`
   (`app/modbus/server.py`, см. ADR-006 п. 1): единое место до обработки запроса,
   где доступны и PDU запроса, и полный контроль над ответом (в том числе
   возможность не отвечать — для timeout). Контекст (`async_setValues`) не
   подходит: из него нельзя «промолчать». Реестр передаётся в сервер через
   `create_server(config, context, injections=…)`; хендлер читает его как
   `self.server.injections`. Порядок проверок в `handle_request`:
   rate-limit (ADR-006 п. 3) → инъекции → нормальная обработка.

2. **Сопоставление запроса с инъекцией** (`find_injection`,
   `app/modbus/injection.py`). Цель инъекции — весь слейв либо диапазон
   `area`/`address`/`count` **по сетке значений** (1,3,… для 32-битных форматов).
   Окно запроса (PDU `address`/`count`, сырые регистры/биты) переводится в
   сетку значений через `touched_bindings` (та же геометрия, что у политики
   записи, ADR-003 п. 3). Совпадение: слейв + область (FC → area) + пересечение
   сеток. При нескольких подходящих инъекциях действует **первая по порядку
   добавления** (детерминированно и просто; пересекающиеся цели — осознанно
   редкий случай). Инъекции применяются только к FC 1,2,3,4,5,6,16; запрещённые
   FC по-прежнему дают Illegal Function (ADR-002, инвариант 5) — гейт FC главнее.

3. **TASK-601 · exception.** Ответ `ExceptionResponse(fc, code)` с кодом
   инъекции (0x01/0x02/0x03/0x04/0x06) вместо обработки: запрос не выполняется,
   чтение не возвращает данных, запись не применяется.

4. **TASK-602 · delay.** `await asyncio.sleep(delay_ms / 1000)` перед
   обработкой (не блокирует loop), затем запрос выполняется штатно — ответ
   и побочные эффекты обычные, только позже. 0..5000 мс — ограничение реестра.

5. **TASK-603 · timeout.** Запрос **поглощается**: ни ответа, ни обработки
   (сервер имитирует отказ отвечать). Молчание активно, пока инъекция жива:
   `ttl_s` для timeout — это и есть длительность молчания (ADR-004 п. 6).

6. **TASK-604 · TTL и автосброс.** Ленивый TTL реестра (без фоновых таймеров,
   инвариант 6) уже есть; enforcement обращается к реестру через `items()`,
   поэтому истёкшая инъекция перестаёт действовать сама — восстановление
   нормального поведения без явного сброса.

7. **Журналирование.** Ответы, сформированные инъекциями, в журнал **не
   пишутся** (по той же причине, что rate-limit: флуд вытеснил бы инциденты из
   ring buffer) — только debug-лог. Жизненный цикл инъекций (`inject`,
   `inject_clear`) журналирует REST-слой (TASK-309).

## Последствия

- Три типа инъекций живут в одном месте (handle_request) и тестируются
  одинаково (serve + клиент); delay использует `asyncio.sleep` — долгие
  инъекции не мешают другим соединениям.
- Поглощение запросов при timeout означает, что запись не применяется —
  документируется в UI (Эпик 7): «timeout скрывает запрос целиком».
- Пересечение инъекций разрешено порядком добавления; при снятии первой
  начнёт действовать следующая — семантика простая, но не «приоритет по силе».
- Привязка к `GuardedRequestHandler` — та же, что ADR-006: пересматривается
  при переходе на pymodbus 4.x.
