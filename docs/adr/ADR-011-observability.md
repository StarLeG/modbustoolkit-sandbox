# ADR-011: наблюдаемость через логи и метрики, без Sentry

- **Статус:** принято
- **Дата:** 2026-10-31
- **Задача:** TASK-907

## Контекст

TASK-907 предлагает «Sentry / structured logs shipping». Sentry требует
зависимость `sentry-sdk`, внешний SaaS и DSN-секрет в окружении. Правила
проекта: ставить пакеты может только пользователь, зависимостей минимум,
секреты живут в env. Экспорт ошибок в чужой облачный сервис - отдельное
решение владельца, а не дефолт публичного сервера.

При этом логи сервера идут через root-логгер без формата: в journald и
docker logs они неструктурированные, шиппить и фильтровать их неудобно.

## Решения

1. **Sentry не вводим.** Ошибки видны двумя штатными каналами: логи и
   счётчики `/metrics` (TASK-904: `modbus_errors_total`, ошибки в окне).
   Когда владельцу понадобится агрегация ошибок, он сам выберет сервис -
   и добавит агент осознанно.

2. **Структурированные логи - `LOG_FORMAT=json`, одна строка JSON на
   событие** (`ts`, `level`, `logger`, `message`, при ошибке `exc`).
   Их шиппит сама платформа: journald (`journalctl -u ... -o cat`),
   docker logs, Loki/ELK на их стороне. Отдельного shipper-а в процессе нет:
   инвариант 6 (event loop не блокируется) не обсуждается даже ради логов.

3. **`LOG_LEVEL` - общий уровень для сервера и uvicorn**, `text` остаётся
   форматом по умолчанию для разработки. Настройка - в
   `app/logging_setup.py`, вызывается один раз при старте (`python -m app`).
